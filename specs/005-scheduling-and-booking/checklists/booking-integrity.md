# Booking Integrity & Concurrency Requirements Checklist: Scheduling Service and End-to-End Booking (Phase 1c)

**Purpose**: Validate that the booking-integrity requirements — overlap, the slot grid, schedule
bounds, grandfathering, the booking horizon, idempotency, and racing attempts — are complete,
unambiguous, and objectively verifiable before implementation begins
**Created**: 2026-08-13
**Feature**: [spec.md](../spec.md)

**Depth**: Lightweight sanity pass. Scope under test: spec.md's FR-016–FR-025, FR-051, FR-058 and
their success criteria, plus the requirement-bearing plan artifacts — [contracts/scheduling.proto](../contracts/scheduling.proto),
[contracts/agent-tools.md](../contracts/agent-tools.md), and [data-model.md](../data-model.md)'s
enforcement table.

## Requirement Clarity & Measurability

- [x] CHK001 Is "overlap" defined at the interval boundary — do an appointment ending at 10:00 and one starting at 10:00 conflict? [Clarity, Spec §FR-016/§FR-017] **RESOLVED 2026-08-13**: new **FR-061** states an appointment occupies `[start, end)`, so back-to-back slots never conflict. Echoed in the Edge Cases, contracts/scheduling.proto, data-model.md, and a quickstart check.
- [x] CHK002 Is the "in the past" boundary specified for an appointment starting exactly at `local_now` — rejected or allowed? [Clarity, Spec §FR-020] **RESOLVED 2026-08-13**: FR-020 now requires the start to be *strictly* after the clock, so the boundary is rejected. The deciding argument is stated with it: FR-031 lists only starts strictly after the same clock, so accepting the boundary would have created an appointment the patient could never see listed. Availability (FR-024), the proto, and research.md #21 were corrected in step — #21 said "starts before `local_now`", which offered the boundary slot and would have made FR-025 false.
- [x] CHK003 Is the 90-day horizon measured from `local_now`'s date or its exact time, against the appointment's start or its end, and is exactly 90 days inside or outside? [Measurability, Spec §FR-021] **RESOLVED 2026-08-13**: FR-021 now fixes all three — exact local date-time (not a whole-day boundary), against the start, boundary inclusive. Only "start, not end" was already implied by the old wording; the other two were open.
- [x] CHK004 Can SC-003 be objectively verified after the fact? [Measurability, Spec §SC-003] **RESOLVED 2026-08-13**: SC-003 reworded to measure *booking attempts* at the instant of the attempt rather than auditing stored rows, and now says explicitly that a grandfathered row outside its practitioner's current schedule is a correct outcome, not a violation.

## Requirement Consistency & Conflicts

- [x] CHK005 Does FR-025's absolute "never offer a time that a booking attempt would then reject" conflict with the simultaneous-booking edge case, which requires the loser of a race to be told the slot is taken? [Conflict, Spec §FR-025 vs Edge Cases] **RESOLVED 2026-08-13**: FR-025 rewritten as a guarantee about the moment of offering, naming the lost race as the one acceptable cause of an offered-then-rejected time and declaring any other cause a defect. SC-009 aligned.
- [x] CHK006 Do FR-024's availability filters enumerate the same predicates that FR-016–FR-021 reject on? [Consistency, Spec §FR-024 vs §FR-016] **RESOLVED 2026-08-13**: FR-024 rewritten — availability is computed for a named patient and also excludes slots colliding with that patient's own appointments with any practitioner. `CheckAvailabilityRequest` gains a required `patient_id`; research.md #21, data-model.md's enforcement table, agent-tools.md, US1-1/US1-5, and the two-practitioners edge case all updated.
- [x] CHK007 Is "excluding them from availability listings" unambiguous? [Ambiguity, Spec §FR-023] It can be read as excluding grandfathered appointments from the offered slots, or from the overlap check used to compute them — opposite meanings, one of which silently permits a double booking. **RESOLVED 2026-08-13**: FR-023 rewritten to say grandfathered appointments count in full for *both* overlap and availability, and that the exclusion refers only to their own time not being offered — which follows from the grid being generated from the current schedule, not from any filtering. FR-024, data-model.md's table, research.md #6/#21, and the proto now say the same thing. The dangerous reading was reachable: a 90-minute appointment grandfathered at 08:00–09:30 under a schedule since narrowed to 09:00 would otherwise leave the 09:00 slot offered and then refused.

## Requirement Completeness

- [x] CHK008 Is the scope and lifetime of an idempotency key specified — global, per patient, or per session — and what must happen when a key already used arrives with a *different* practitioner or start time? [Gap, Spec §FR-051] **RESOLVED 2026-08-13**: FR-051 now replays only when the request matches the stored appointment; new **FR-063** refuses a mismatch with `INVALID_ARGUMENT` (returning neither the stored nor a new appointment); new **FR-062** requires the key to be a function of patient/practitioner/start; new **FR-064** fixes the scope as global and the lifetime as the appointment's. This was not merely unspecified — the old wording *mandated* replaying the stored appointment for a mismatched request, which would have confirmed a time the patient never chose.
- [x] CHK009 Is it specified whether a key is consumed by a *refused* attempt, i.e. whether retrying with the same key after a refusal re-evaluates the request or replays the refusal? [Gap, Spec §FR-051] **RESOLVED 2026-08-13**: FR-064 — a key is recorded only when an appointment is created, so a refusal leaves it free and a later attempt is evaluated afresh. Resolved together with CHK008; the two are clauses of one rule.
- [x] CHK010 Is the requested availability period bounded by any requirement? [Gap, Spec §FR-024] The plan caps it at 14 days and 50 returned starts (research.md #21, contracts/scheduling.proto), but no spec requirement constrains either. **RESOLVED 2026-08-13**: new **FR-067** states both caps, requires an over-wide request to be clamped rather than refused, and requires truncation to be reported — the last part being what lets the assistant tell a fully-booked window from one it never saw the end of. An Assumptions bullet records that both numbers are chosen, not derived.
- [x] CHK011 Are requirements defined for an appointment duration that no working range can contain — e.g. a 120-minute duration against a 60-minute range? [Gap, Spec §FR-007] The empty-schedule case is covered in Edge Cases; this one produces the same "listed but never bookable" outcome and is not. **RESOLVED 2026-08-13**: the outcome was already derivable from FR-019's whole-slots rule, so this was a legibility gap rather than an open decision — FR-019 now says it outright ("a range shorter than one appointment duration yields no slots at all"), a matching Edge Case says the practitioner is still listed and the assistant says they have no bookable times, and agent-tools.md's `bookable` flag is redefined to cover it rather than only an empty schedule.
- [x] CHK012 Are requirements defined for two *contiguous* working ranges on one weekday (08:00–12:00 and 12:00–16:00)? [Gap, Spec §FR-006/§FR-018] Nothing forbids them — FR-006 only forbids overlap — and whether an appointment may span their junction is unstated. **RESOLVED 2026-08-13**: FR-006 now permits contiguity explicitly and keeps the ranges distinct; FR-018 requires an appointment to fit inside a *single* range and names the junction case; FR-019 anchors each grid at its own range's start. A worked Edge Case (a 90-minute practitioner offering 08:00, 09:30, 12:00, 13:30) makes the consequence concrete. The old wording answered the spanning question only if a reader weighted "one of" heavily.

## Scenario & Failure Coverage

- [x] CHK013 When a requested start falls inside no working range at all, is it specified which refusal reason applies — outside-schedule or off-grid? [Gap, Spec §FR-018/§FR-019] Both exist in contracts/scheduling.proto, and FR-029 requires the patient be told which. **RESOLVED 2026-08-13**: new **FR-065** answers it — outside-schedule, "never an off-grid one; off-grid presupposes a range to be off the grid of" — as one case of a full precedence over all eight reasons. A quickstart negative check (ask for a Sunday) exercises it.
- [x] CHK014 Is the outcome specified when a booking names a practitioner or patient belonging to another session — a distinct refusal, or deliberately indistinguishable from not-found? [Completeness, Spec §FR-008/§FR-002] **RESOLVED 2026-08-13**: new **FR-066** — indistinguishable, deliberately. A distinct "belongs to another session" refusal would confirm that a guessed identifier is real, which is the disclosure FR-002/SC-004 exist to prevent. Reflected in the proto's two `NOT_FOUND` reasons and in data-model.md's enforcement table (the session filter is what makes it true without extra code), and now asserted in T047.
- [x] CHK015 Is there a stated mapping from each refusal reason a patient can be given back to the requirement that produces it? [Traceability, contracts/scheduling.proto vs Spec §FR-016–§FR-021] The contract defines eight reasons; the spec states six rejection rules, with no requirement tying the two sets together. **RESOLVED 2026-08-13**: FR-065 enumerates the closed set of eight in the spec itself, maps each to its rule, and closes the count gap that made the mismatch hard to see — the two "extra" contract reasons are the not-found pair, which FR-008/FR-066 produce. It also fixes the reason when several rules break at once, so a refusal is a property of the request rather than of the implementation's checking order.

## Notes

- Check items off as completed: `[x]`
- Each item tests whether the **requirement** is well written — not whether an implementation behaves
  correctly. A checked box means the spec (or a contract it delegates to) now answers the question,
  not that code passes.
- Items whose answer lives only in a plan artifact are still findings: the plan settled them, but the
  spec did not, so nothing prevents the decision drifting the next time the spec is revised.
