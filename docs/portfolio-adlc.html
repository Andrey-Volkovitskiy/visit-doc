visitdoc.app: Agentic Development Lifecycle

Every line of code was written by a coding agent (Claude Code), steered through spec-driven development (SDD). I decided what to build and why, and built the guardrails that keep the agent's output production-grade, so I could run several features in parallel and spend my time on design and verification.

The loop: the engineer decides and verifies, the agent builds

Guardrails against agent drift

  • Spec-kit as the backbone: specs, contracts, data models and task lists give parallel subagents one reference, let behaviour be checked against intent, and keep big features from bloating the context, since a fresh session picks up from the files.
  • Written principles the agent follows. A spec-kit constitution, code-style and testing guides, and a CLAUDE.md per service set the project's rules, e.g. "one value, one meaning" (no status or empty result may stand for two situations) and non-negotiable TDD: tests are written from the spec before the code exists, so they have no code to mirror.
  • 4,800 tests (unit, integration, end-to-end) catch regressions. Each test worker gets its own Postgres databases and Qdrant collections, so several coding agents can check their edits at the same time without collisions.
  • Hooks. After every edit, code is auto-formatted, linted and type-checked. Errors go straight back to the agent, so a type error never survives to the next step.
  • CI on GitHub Actions runs pre-commit, unit, frontend and integration tests on every push.

Token and time efficiency

  • Context ready from the first prompt. The current architecture lives in the roadmap, each feature's details in its spec, and the dev tools and commands in the CLAUDE.md files, so a new session starts with the project and its environment already known instead of spending time exploring.
  • Session post-mortems. Coding sessions are analysed afterwards, and each lesson becomes a new agent instruction (e.g. a full eval run spent where a targeted one would do), so the same pitfall isn't hit twice.
  • A custom skill for every repeated routine: speckit-analyze-loop (cross-check the spec documents until they agree), speckit-implement-loop (implement → converge until nothing is left), review-loop (rounds of high-effort code review and fixes) and commit-changes (conventional commits).

While the agents run: where my time goes

  • Other features in parallel, each in its own git worktree, with isolated tests.
  • UI design by handing the agent a sketch to build from.
  • Verifying results by measurement, not opinion: against golden cases, compared with the baseline and its noise band.
  • Analysing the assistant in Langfuse: its behaviour, latency and cost.
