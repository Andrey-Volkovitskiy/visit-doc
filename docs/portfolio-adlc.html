visitdoc.app: Agentic Development Lifecycle

Every line of code was written by a coding agent (Claude Code). My job was the engineer's part: decide what to build and why, set guardrails so the agent couldn't drift, review the result, and make the decisions only a human should make. The result is a production-shaped multi-service AI app, built with spec-driven development (SDD).

The loop: the engineer decides and verifies, the agent builds

Guardrails I designed for the agent

  • Spec-driven development (spec-kit). 18 features, each with a spec, plan, research notes, data model, API contracts, tasks and quickstart. A constitution with eight principles binds every plan and makes TDD non-negotiable: every behaviour starts as a failing test.
  • A binding roadmap as the statement of intent. Each phase states what to build and the reasoning behind it. Every technology choice and its tradeoff is recorded beside the phase that made it (21 sections).
  • Hooks. After every edit, Python is auto-formatted, linted and type-checked with strict mypy, and TypeScript runs tsc -b. Errors go straight back to the agent, so a type error never survives to the next step.
  • Custom skills that automate the cycle: speckit-analyze-loop (cross-check the spec documents until they agree), speckit-implement-loop (implement → converge until nothing is left), review-loop (rounds of high-effort code review and fixes) and commit-changes (conventional commits).
  • Layered agent instructions. Each directory has its own CLAUDE.md, loaded only when the agent works there. Project-wide principles (e.g. "one value, one meaning", "a timeout never proves the server did nothing") turn hard-won lessons into rules the agent follows.
  • UI sketches before UI code. Three static HTML mockups filled with the product's real content, from conventional to experimental. One was chosen and made the visual reference; the agent implemented against it.

Verification I don't delegate

  • Test pyramid: unit, integration (real Postgres and Qdrant) and end-to-end in a real Chromium via Playwright. CI on GitHub Actions runs pre-commit, unit, frontend and integration tests on every push.
  • Isolated test runs, so several agents can work at once. Each coding-agent session, and each parallel test worker, gets its own Postgres databases and Qdrant collections, named automatically. Several agents can run the full suite at the same time without clearing each other's data.
  • AI behaviour is gated by evaluation, not by opinion. A prompt change is replayed offline first, then run on only the golden cases it can affect, and only then on the full set, compared with the baseline and its noise band.
  • Lessons become rules: each costly mistake (e.g. a full eval run spent where a targeted one would do) becomes a written rule the agent follows.
