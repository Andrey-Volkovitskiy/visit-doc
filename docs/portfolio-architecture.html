VisitDoc: architecture

Two services, one deliberate boundary · Andrey Volkovitskiy · github.com/Andrey-Volkovitskiy/visit-doc

Strongest architectural decisions

  • One deliberate service boundary. Scheduling is split out because its invariants need the schedule and the appointments in one transaction. Each service has its own database, and the two refer to each other only by opaque id, with no cross-database foreign key.
  • Integrity lives in the database. Double-booking is ruled out by PostgreSQL exclusion constraints on time ranges. A reschedule is one conditional UPDATE whose WHERE clause carries the staleness check, never a read followed by a write.
  • Postgres decides what Qdrant may answer from. FAQ writes add new revisions and publish them in one commit, so a half-failed write never leaves a stale or orphaned chunk that can be retrieved.
  • Tenant scoping on every query, as a WHERE predicate, never as a filter applied afterwards, even for lookups by a unique id.
  • Failure semantics are designed in. A timeout never proves the server did nothing: an unknown write outcome is stored and shown as unknown, not retried. Any turn that ends without a reply calls a person.
  • Dependency inversion around providers. The agent graph sees only domain types. Each provider call converts to its own wire format internally, and tracing goes through one module that is the only place allowed to import Langfuse.
  • "One value, one meaning". No status or empty result stands for two different situations. Distinct outcomes get distinct types, so the agent can't turn an ambiguity into a confident false statement.
  • Typed contracts across the boundary: a shared gRPC proto and shared Pydantic models live in workspace packages of a uv monorepo, so both services use the same definitions.

Delivery and operations

  • Test pyramid: 4,660 unit (4,072 Python + 588 frontend), 74 integration (real Postgres, Qdrant and gRPC) and 8 end-to-end journeys in a real Chromium against the running stack. Coverage: 96% of Python statements and 94% of frontend lines.
  • Run locally three ways: as plain processes with hot reload, as Docker Compose (three images, migrations as one-off containers), or in a local Kubernetes cluster (k3d) behind a Traefik Ingress, with Kustomize base and overlays. Images are pushed to GHCR tagged by commit, and a deploy restarts only the services whose image changed.
  • Observable by construction: structured JSON logs with secrets redacted by key name and by value, Langfuse traces per agent step, and the token cost of every model call logged.
